Rootless Qwen sandbox for Arch Linux and an active nvm/global npm install.

Arch package: qwen-isolated-git (AUR; planned, not yet published).
The package installs /usr/bin/qwen-isolated and its sandbox dependencies.
Qwen must be installed in the Node prefix selected by your active node.

Run from a Git repository or one of its subdirectories. The nearest .git
directory or regular file selects the entire mounted repository subtree,
including repositories using .git files for worktrees or submodules. Qwen starts
in the corresponding subdirectory. Search stops before your home directory or /.
Marker symlinks are rejected. No custom approval marker is needed.
This applies to all sandbox modes.

Usage:
  qwen-isolated                    Start Qwen
  qwen-isolated --shell            Inspect the sandbox
  qwen-isolated --check            Test filesystem, privileges and networking
  qwen-isolated --isolation-help   Show this help

Configure models, endpoints, and authentication in Qwen Code's own settings:
  /home/qwen/.qwen/settings.json inside the sandbox
  ~/.local/state/qwen-bwrap/<repository-path-hash>/home/.qwen/settings.json on the host
Use --shell to access this persistent, per-repository home. Your host's ordinary
~/.qwen settings are not exposed. API keys can be loaded by Qwen from the
sandbox home's ~/.qwen/.env or the settings.json env field. No OPENAI_* shell
exports are required; existing OPENAI_BASE_URL, OPENAI_API_KEY, and OPENAI_MODEL
variables are optionally forwarded. See the README for a settings.json example.

Public IPv4 destinations are allowed; host/LAN and IPv6 egress are blocked.
The selected model's baseUrl in the sandbox's user settings automatically grants
an exact IPv4/TCP exception, e.g. http://192.168.1.50:11434/v1 allows only
192.168.1.50:11434. No separate model-server environment variable is needed.
Use model.name and security.auth.selectedType to select the model; model.baseUrl
distinguishes duplicate model IDs. CLI model overrides are considered too.
LAN exceptions require literal IPv4 addresses. Hostnames use ordinary filtered
networking. Repository settings and .env files do not grant exceptions; .env
files can still supply API keys to Qwen. The settings env field can supply
endpoint variables. Relaunch after changing the model endpoint. --shell grants
no model exception and remains available to repair invalid settings.
Extra blocked IPv4 LAN/VPN prefixes, separated by spaces or commas:
  export QWEN_ISOLATED_DENY='203.0.113.0/24 198.51.100.0/24'

Trusted setup creates a private user/network namespace, loads nftables inside
it, and attaches host-side slirp4netns. Qwen then runs inside Bubblewrap in a
child user namespace with no authority over that firewall. Setup failure never
falls back to unrestricted networking. No sudo or host firewall changes.
Namespace UID 0 maps to your ordinary host UID. No host root privilege is used.

This is direct-destination filtering, not a prohibition on internet relays,
VM, resource quota, or syscall allowlist. Remote MCP services have their own
scope. Relaunch after LAN/VPN route changes. Keep this launcher outside
writable sandbox mounts. The original per-project sandbox home is preserved.
